# Endless Nightlord Gauntlet - a DoubleBOSS (Nexus #952) variant

**Version 1.0.4** - see [CHANGELOG.md](CHANGELOG.md).

If you played 1.0.0-1.0.3 you saw the chain stop after the second Nightlord: the results screen
rolled even though the loop events themselves were looping. The reason was outside the loop. The
maps' own boss-death handlers (and one direct `FinalizeExpedition()` call in `m18`) still ran
their stock "expedition finished" tail, which sets flag `7512`. Every one of those paths is now
disabled: nothing in these scripts can roll the results screen any more, so the chain only ends
when the team is wiped.

Built on top of **DoubleBOSS** by the original author. Same delivery format (a `mod/`
folder loaded by a **me3** profile with Seamless Co-op), same assets - only the event
scripts are changed.

**What DoubleBOSS does:** after you kill the expedition's Nightlord it does not roll the
results screen. It warps the team back into the arena and spawns a second, random
Nightlord for one more fight; killing that one ends the run.

**What this variant does:**

| | DoubleBOSS | This mod |
|---|---|---|
| Chained Nightlord fights | exactly 1 | **unlimited**, until the run actually ends (team wipe / abort) |
| After each chained kill | results screen | next Nightlord spawns, kill is counted |
| Consumables | none | **replenished every 3 chained kills** (`REFILL_EVERY`, see below) |
| Which Nightlord | random once per expedition | **a fresh random Nightlord every round** |
| Difficulty ramp | - | none; every round is a fresh full-HP boss |

A complete, mechanism-level description of every capability (and of what the mod does *not*
do) is in [`CAPABILITIES.md`](CAPABILITIES.md).

## 1. Ready to play - nothing to compile

The four map scripts are **already compiled and included**:

    mod/event/m16_00_00_00.emevd.dcx     (Storm + one other expedition map)
    mod/event/m16_10_00_00.emevd.dcx
    mod/event/m18_00_00_00.emevd.dcx
    mod/event/m19_00_00_00.emevd.dcx

This download contains only what the game loads - no source files, no build tools. The
`.emevd.dcx.js` sources the four files were built from live in the project repository
(`mod/event/`), together with `tools/`; you only need them if you want to change the behaviour.
Editing workflow: open a `.js` in
[DarkScript3](https://github.com/AinTunez/DarkScript3/releases) (Nightreign support), edit,
**Ctrl+S** - it writes the matching `.emevd.dcx`. Keep `common_func.emevd.dcx` in the folder
while compiling; the scripts are `@linked` to it.

How they were built (Linux, no Windows/Oodle needed) is documented in
`tools/compiler/README.md` in the repository. The shipped `.dcx` files use DCX **DFLT** (zlib) compression
instead of the retail DCX_KRAK, because Oodle compression is Windows-only. Same DCX
container, different codec; recompiling in DarkScript3 on Windows produces KRAK again.

## 2. Install

1. Copy the whole `EndlessNightreign` folder anywhere.
2. Put **Seamless Co-op for Nightreign** in `EndlessNightreign/SeamlessCoop/` so that
   `nrsc.dll` sits at `EndlessNightreign/SeamlessCoop/nrsc.dll` (exactly what the original
   DoubleBOSS profile expects).
3. Launch through **me3** and pick `EndlessNightreign.me3`.

`savefile = "NR0000.co2"` and `start_online = false` are unchanged from the original.

Sources: `mod/event/*.dcx.js` in the repository (generated by `tools/endless_transform.py`). The
build inputs for the compiler - the decompiled original scripts used as init data - are
regenerable with `tools/original_inits.json`; see `tools/compiler/README.md`.
`mod/map`, `mod/msg`, `mod/regulation.bin` and `common_func.emevd.dcx` are the original
files, untouched - this is purely an event-script mod.

## 3. Configuration

Everything is generated by `tools/endless_transform.py`; change the two constants at the top
and rerun it from the folder containing `DoubleBOSS/` to regenerate the `EndlessNightreign/`
sources (then recompile, step 1):

```python
REFILL_EVERY = 3        # 0 = no refill at all
REFILL_SPEFFECT = 509   # spEffect applied to each player on a refill
```

`509` is the restore the game itself applies on a boss kill. If your consumables are not
restocked by it, swap in the spEffect (or flag/item instruction) that does - the block is
repeated verbatim in each of the four scripts under
`// 3 bosses defeated: replenish consumables`, so it can also be hand-edited.
Counter flags: `19300101`/`19300102` (kills since last refill), `19300002` (first round
played); all cleared in `19110900` on run start.

## 4. What was changed in the event scripts

Flags kept from the original: `7512` = "a Nightlord is down" latch (the stock arena events
stop themselves once it is ON, and the stock death handler that sets it is what finalises the
expedition), `19002951` = start
chained fight, `19002952` = team warped / boss may spawn, `19002953` = chained fight live,
`19002954` = map boss defeated latch, `19002955` = boss spawning, `19002956/57` = chain armed.

Per map script (`m16_00`, `m16_10`, `m18_00`, `m19_00`):

1. **`19002951` (round manager)** - the one-shot "warp the team into the arena" transition is
   now a loop: clear `19002952/53/55`, show the "next Nightlord" interlude, warp everybody,
   set `19002952`; wait until the death handler clears `19002952`; repeat. The first interlude
   keeps the original 8 s + 3 s + text `6015`, later ones are 4 s.
2. **`19114900`-`19114905` (per-Nightlord spawn)** - each spawn event loops instead of ending:
   wait for `19002952`, re-`EnableCharacter` the boss (the death handler disabled the corpse),
   play the original entrance sequence, set `19002953`, then wait for the round to finish.
3. **`19309000` (new; replaces the stock death handler for the chained boss)** - the same
   defeat feedback the game gives (`IncrementTeamBossesKilled`, SE, `RecordUserDispLog`, BGM
   stop, health bar hidden, heal `509`, victory text) but it **never sets `7512`**, so the
   stock wind-down never happens and the arena keeps running instead of finalising the
   expedition. It counts the kill, runs the refill block every N kills,
   and disables the corpse for the next round. Registered instead of common_func `90075901`
   for 圣牢布 / 米塔恩 / 王三狼 / 王人马 / 王冰龙, and instead of `190075904` for 垃圾王.
4. **`190017580`** (extra 圣牢布 death handler that ended the run) - no longer initialized.
5. **`19110900`** - arms **all six** Nightlord families (the original arms only the one
   `RandomAppearLot` rolled, which is why DoubleBOSS always repeats that one) and clears the
   round-pick flags on run start.
6. **Per-round lottery** - at the start of every round the manager sets one random flag out of
   `19300010`-`19300015` with `RandomlySetNetworkconnectedEventFlagInRange`; it then resolves
   the result into exactly one of `19300020`-`19300025` (first match wins, with the first
   family as fallback, so the round can never stall), and only that family's spawn event and
   death handler react to the round. The flags are network-connected, so all co-op peers see
   the same pick.
7. **The "expedition finished" paths are disabled.** The stock death handlers of each map
   (events `190075901`, `190075904`, `290075904`) no longer reach their second half - the tail
   that applies the victory spEffect, counts the kill and sets flag `7512`. After the first kill
   they park instead. The 30 s "next round never started" fallback that also set `7512` is gone,
   the "chain is not armed" branch now arms the chain instead of ending the run, and m18's spare
   `FinalizeExpedition()` call is gone. Verified on the compiled files: no instruction in any of
   the four scripts writes `7512` any more.
8. **Golem and scarab removed** - `19110900` now disables `19110888` (golem) and sets the chain
   gate `19002957` itself, instead of waiting for the golem to die before the chain can start;
   the scarab `19214191` is disabled at map load and its job (unlocking the invading second
   Nightlord, flag `19002973`) is done directly when the boss reaches 70 % HP. See section 8 of
   `CAPABILITIES.md`.

## 5. Known risks (please read before reporting a bug)

This was written by reading the mod's decompiled scripts, **not** by playing it - I could not
run Nightreign here. The scripts do compile cleanly, and rebuilding the *unmodified* original
scripts with the same toolchain reproduces the retail `.emevd` files byte for byte, so the
compiler path is sound - but the game logic itself is untested. Check these first, in order:

0. **Loading.** If the game refuses to load the event files at all (crash on map load, or the
   expedition never starts), the suspect is the DFLT (zlib) compression of the shipped `.dcx`.
   Fix: recompile the four `.js` in DarkScript3 on Windows and use those `.dcx` files.
1. **Boss revival.** Round 2+ depends on `DisableCharacter` + `EnableCharacter` respawning the
   Nightlord at full HP (that is what the mod's own entrance events do). If a boss comes back
   already dead, invisible, or at 1 HP, this is the thing to fix.
2. **垃圾王 (two-phase boss).** Its phase transition and the endless loop both drive
   `19002953`; the loop clears that flag on death, which could cut a phase-2 transition short.
3. **BGM / health bar leftovers** between rounds for 米塔恩 and 王冰龙, whose entrance events
   were written to run once.
4. `IncrementTeamBossesKilled(1)` now fires every round; if the game ends the expedition on its
   own after a fixed number of team kills, the run would still stop after that many kills even
   though the scripts never ask for it. This is the one remaining way the run can end besides a
   team wipe.
5. Interlude timing: 4 s between later rounds may be too short while the team loots - raise
   the `WaitFixedTimeSeconds(4)` in the round manager.
6. **Round lottery.** If a round starts and no Nightlord shows up (the fight flag `19002953`
   never comes on), the roll/selection path is the suspect: inspect `19300010`-`19300015`
   (raw roll) and `19300020`-`19300025` (resolved pick) in a flag debugger.
   `RandomlySetNetworkconnectedEventFlagInRange` is a stock instruction the game itself uses,
   but it is called from a map event here. If co-op peers disagree on the pick, the resolved
   flags are the place to look; worst case, replace the roll with a fixed family order.
7. All six families' init events now run at run start, so all their per-family common-event
   registrations (BGM heat-up, health-bar links, buffs) are live at once. That is what makes
   rotation possible and is the part I would watch most closely in the first real session.

## 6. Rollback

The untouched original is the `DoubleBOSS/` folder in the project repository (and Nexus mod
#952 itself); its compiled `.dcx` files are the unmodified two-boss version, so switching back
to `DoubleBOSS.me3` restores the original behaviour.
